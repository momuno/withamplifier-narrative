The Problem

Many vendor SDKs are black boxes at the orchestration layer (often CLI-wrapped).

Locked Agent Loops
Every vendor ships the same pattern: your app wraps their binary or fixed runner class. You observe their agent loop. You can't change how the agent thinks. Two of the three major SDKs literally wrap CLI binaries as subprocesses.
Vendor Lock-In All the Way Down
Two of the three major SDKs still enforce deep vendor lock-in (binary or model). OpenAI’s is more flexible but still owns the loop.
Hooks That Only Watch
Vendor hooks let you observe and gate. That's it. No contributing back to the conversation. No self-correction. No feedback loops. The agent makes mistakes and you have no structural way to help it learn.
The Solution

Amplifier

A modular AI agent framework.
Provider-agnostic. Fully extensible. Completely observable.

Part 1

Architecture

Built on Linux kernel principles

Key Distinction

Amplifier is not one thing

As a Tool
The App CLI competes with Claude Code, Copilot CLI, Codex CLI. It's good enough that we use it daily and continue evolving it. This is what you'll touch first.
As a Platform
The kernel + modules act as an agent SDK — with no dependency on our CLI. You can build your own applications, your own orchestrators, your own tools. No other SDK offers full, first-class replacement of both orchestrator and memory modules.
Most people see the CLI and compare it to other coding tools. But underneath is a platform. No one has found the right agent abstraction yet — Amplifier lets you try things, swap what doesn't work, and keep what does. The CLI is proof the platform works. The platform is why the CLI evolves so fast.
Design Philosophy

Built on Linux kernel principles

  • ✓ Mechanism, not policy — Kernel provides building blocks, not dictates
  • ✓ Tiny kernel — Core is ~2,600 lines, stable and minimal
  • ✓ Powerful modules — All features live at the edges
  • ✓ Event-driven — Everything emits events for observability

Module System

Five module types

Each satisfies a Protocol contract from the kernel. Swap any module without touching the kernel.

  • ✓ Providers — LLM backends (swap models freely)
  • ✓ Tools — Agent capabilities (LLM decides when to call)
  • ✓ Orchestrator — The main engine (controls the LLM-tool-response loop)
  • ✓ Context — Memory management (conversation history, compaction)
  • ✓ Hooks — Lifecycle observers (code-decided, not LLM-decided)
Module Deep Dive

Providers: Your Model Layer

Every provider satisfies the kernel's Provider Protocol contract: complete(request) → response. Swap any provider without touching the kernel or your application.

Provider Agnostic
Anthropic, OpenAI, Azure OpenAI, GitHub Copilot, Google Gemini, Ollama, AWS Bedrock, and more. Configure multiple — switch with one line.
Different Models per Agent
Sub-agents can be invoked with different models. Use Opus for your main loop, Haiku for lightweight agents, GPT-4o for specific tasks — all in the same session.
Build Your Own
When a new model drops, build a provider module. Satisfy the Protocol contract and it works. Don't wait for a release from us.
Module Deep Dive

Tools: Agent Capabilities

Tools are capabilities the agent can invoke. The LLM decides when to call them — file I/O, shell, search, web, and more.

Build Your Own
If a tool is missing, build your own module. Proprietary tools specific to your business, your APIs, your workflows. Don't wait for us.
Extensibility Built In
MCP servers and Skills are supported through existing tool modules. The common extensibility points you'd expect — plus the ability to go deeper.
Deep Dive

The Orchestrator: Your Control Surface

The orchestrator controls the entire execution loop. Swapping it can radically change agent behavior.

“We would not make that choice again. The differences between models are significant enough that you will need to build your own agent abstraction.”
— Armin Ronacher, creator of Flask, CTO of Sentry
Real example: Opus is powerful but likes to do all the work itself — it won't delegate to specialized agents. When context fills up (200K limit), it starts losing earlier conversation. Solution: Use an orchestrator that removes direct tool access, forcing Opus to delegate to sub-agents. Each agent gets fresh context. The main loop stays lean and runs longer.
Tip: You can build your own orchestrators for your specific applications — this is something no other AI coding tool lets you do.
Module Deep Dive

Context: Memory Management

Context modules manage conversation history and the context window. The default strategy: as you approach the limit, remove old tool results first, then trim older conversation.

This is something you cannot do in other tools. In Claude Code, whatever context management they built is what you get. In Amplifier, you can build your own: write forgotten context to disk, leave breadcrumbs for the AI to read back, implement RAG-based retrieval — whatever strategy fits your problem.
Module Deep Dive

Hooks that contribute, not just observe

The 5-action precedence chain:

deny
>
ask_user
>
inject_context
>
modify
>
continue
Vendor SDK Hooks
Hooks exist, but are mostly observational—not a full control surface.
Amplifier Hooks
All of the above, plus: inject context into the agent's next turn, modify tool arguments in-flight, escalate to user. The agent writes code, a hook catches errors, inject_context tells the agent what's wrong, the agent self-corrects — no human needed.
This is code-decided, not LLM-decided. A logging hook always fires. A linter hook always runs. The LLM doesn't choose whether to get feedback.
Module Workflow

Amplifier can help you build Amplifier

If you think you need a new module, discuss it with Amplifier first. Run it by the amplifier-expert agent. It can help you design the contract and build the module — this isn't a separate, daunting process.

Very different from vendor SDKs: you don't wait for the vendor to ship a feature. You can extend the platform yourself, with the platform's help.
Part 2

Context Management

Why Amplifier sessions feel different

Context management is more important than prompting.

The best prompt in a polluted context will fail.
A simple prompt with clean context will succeed.

Context Discipline

Don't load everything yourself

  • ✓ Use targeted reads—specific files, not entire directories
  • ✓ Let sub-agents fetch what they need—don't pre-load
  • ✓ Use grep and glob to find before reading
  • ✓ Context files in bundles load automatically—design them well
  • ✗ Don't read 50 files "just in case"
Sub-Agent Strategy

When to delegate to sub-agents

Specialized Tasks
Bug hunting, security review, architecture design—delegate to agents with specialized context.
Fresh Context
When your context is bloated, spawn a sub-agent with just what it needs. Clean slate.
Parallel Work
Need to research while implementing? Spawn parallel sub-agents. Work concurrently.
Context Inheritance

Three inheritance modes

Mode Behavior Use Case
none Child starts fresh Privacy-sensitive tasks, stateless ops
recent Pass last N turns Most common — recent context without overflow
all Pass entire history Full conversation context needed
Coordinator + Specialists pattern: Parent tracks high-level plan. Sub-agents get minimal, focused context. Results flow back up for integration.

Part 3

Recipes & Workflows

Multi-step agent orchestration

The Problem

Why recipes exist

Multi-Step Tasks
Complex workflows involve multiple agents in sequence. Orchestrating them manually is error-prone.
Repeatability
You run the same workflow repeatedly. Writing it as code makes it consistent and versioned.
Interruptions
Long-running work gets interrupted. You need to resume exactly where you left off.
Anatomy

YAML workflow definition

name: code-review-workflow description: Review and deploy code changes steps: - id: analyze agent: foundation:explorer output: analysis prompt: "Analyze changes in {{file_path}}" - id: review agent: foundation:zen-architect prompt: "Review code quality: {{analysis}}" # Approval gates for human-in-loop stages: - name: review steps: [analyze, review] approval: required: true prompt: "Approve deployment?"
Capabilities

What you get

Context Accumulation
Use output field to create named variables, then reference directly: {{analysis}}
Approval Gates
Pause for human review at critical checkpoints. Agent waits for your decision.
Automatic Checkpointing
Every step completion is saved. Resume interrupted workflows seamlessly.
Provider Selection
Specify provider and model per step. Use Haiku for simple steps, Opus for complex ones.
Parallel Execution
Use parallel: N on foreach loops to run iterations concurrently.
Conditional Logic
Skip steps based on conditions. Branch workflows dynamically.
Lessons Learned

Building Recipes: A Real Story

  • 1 Started with a complicated set of manual steps for PR review — code review + cross-repo contract validation + runtime testing in a shadow environment
  • 2 Built a recipe to automate it. Ran it on a teammate's PR. Recipe “passed.” We merged.
  • 3 The app crashed immediately.
What happened: The recipe YAML had a syntax error. Opus read the recipe file, saw what we were trying to do, and did it itself — skipping critical steps. The output looked identical to a recipe run.

Result: We discovered a cross-repo contract violation AND a missing runtime check. Spent the rest of the day refining the recipe — and built a mode that restricts the agent to ONLY the recipe tool, so it can't improvise.
Best Practices

Recipe Development Checklist

Verify It's Actually Running
The LLM may read your recipe and do the work itself instead of executing it. Use modes or tool restrictions to ensure deterministic execution.
Validate Against Known Failures
Test your recipe against cases where you KNOW there's a problem. If the recipe passes a known-bad case, it's not actually checking.
Iterate, Don't Expect Perfection
Recipes are built iteratively from real work. Mine your successful sessions for processes, encode them, then refine against real PRs and real failures.

M365 in 60 Minutes

Every person on our team set up a private M365 tenant. None of us knew M365 administration. We pointed Amplifier at it and started collaborating.

What Happened
Amplifier configured security, set up authentication, and within an hour each person had Amplifier sending Teams messages, managing SharePoint, and driving M365 from the command line.
Why It Worked
M365 has golden paths and stable documentation. The AI agents could follow them. When docs are good, AI excels.
The kernel doesn't know what it's orchestrating. M365 administration, infrastructure setup, security configuration — the same framework that writes code can drive any domain with good documentation.
